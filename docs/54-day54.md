# 第 54 天：插件微服务镜像瘦身与 Docker 层压平

### 一、今日目标
- 解决 OCR 微服务镜像体积暴增至 23GB 的痛点，缓解磁盘压力。
- 通过 Docker 层压平（export/import）技术，剥离历史无用的临时缓存与构建层。
- 固化标准 `/health` 健康检查端点，摆脱对 `/openapi.json` 的依赖。

### 二、核心实现

#### 1、Dockerfile 瘦身尝试
在 Dockerfile 中的各个 `RUN` 层末尾追加了清理命令：
```dockerfile
RUN pip3 install ... && rm -rf /root/.cache/pip /tmp/* /var/tmp/*
RUN apt-get clean && rm -rf /var/lib/apt/lists/* /usr/share/doc /usr/share/man
```
但由于 Docker 的联合文件系统（UnionFS）分层机制，如果在后面的层里删除文件，**只会在当前层打上“已删除”的标记，底层的文件依然存在**。这导致实际逻辑虚拟体积不降反增（达到了 23GB）。

#### 2、终极压平方案（docker export / import）
为了彻底抹除历史层，剥离所有冗余的 `.whl` 压缩包和废弃缓存，采用了容器导出并重新导入的方案：

1. 从镜像创建临时容器：
   `docker create --name ocr-temp oj-plugin-ocr_plugin-service:0.3.0`
2. 导出文件系统为 tar 包：
   `docker export ocr-temp -o ocr-slim.tar`
3. 重新导入并重建环境变量与启动命令：
   ```bash
   docker import -c "WORKDIR /app" -c "CMD [\"uvicorn\", \"main:app\", \"--host\", \"0.0.0.0\", \"--port\", \"8001\"]" \
     -c "ENV PYTHONUNBUFFERED=1" \
     -c "ENV LD_LIBRARY_PATH=/usr/local/cuda/lib64:..." \
     ocr-slim.tar oj-plugin-ocr_plugin-service:0.3.0
   ```
4. 删除旧镜像与临时 tar 包。

**成果**：逻辑体积从 `23GB` 降至 `19.2GB`，**实际磁盘占用从 `7.69GB` 降至 `6.26GB`**。剥离了约 4GB 的历史无用层。对于包含 PyTorch 与 Paddle 双框架及 CUDA 库的镜像来说，6.26GB 已经是极佳的物理极限。

#### 3、固化 `/health` 路由
- 在 `service/main.py` 中明确增加了 `@app.get("/health")`。
- 将 `ocr_plugin/__init__.py` 里的探测目标从 `OCR_SERVICE_URL/openapi.json` 改回了标准的 `/health`，确保与主流微服务规范对齐，提升插件安装时的健康检查成功率。

### 三、踩坑记录

#### 1、PyTorch 海外源断连
**现象**：构建时拉取 `torch==2.4.1+cu121` 连续 6 次断连，报 `incomplete-download`。
**原因**：海外官方源在国内网络极不稳定，而阿里云镜像没有同步 CUDA 版本的包。
**解决**：使用上海交大镜像源（`https://mirror.sjtu.edu.cn/pytorch-wheels/torch_stable.html`），经过 2.5 小时的断点续传最终拉取成功。

#### 2、`docker import` 丢失 `WORKDIR`
**现象**：压平后重新运行镜像报 `ERROR: Error loading ASGI app. Could not import module "main"`。
**原因**：`docker export` 不会保留原镜像的 `WORKDIR`，导致 uvicorn 在根目录下找不到 `main.py`。
**解决**：在 `docker import` 时强制通过 `-c "WORKDIR /app"` 指定工作目录。
