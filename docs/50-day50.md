# 第 50 天：拍照智能录题插件（PaddleOCR 微服务）

### 一、今日目标
- 搭建独立的 PaddleOCR 微服务容器。
- 解决底层 C++ 库缺失与 Python 依赖问题。
- 主后端通过 httpx 调用微服务，并接入插件系统。
- 前端实现拍照、预览、批量入库闭环。

### 二、核心实现

#### 1、独立微服务化（ocr_service）
- 在 `backendocr_service` 目录下独立编写 Dockerfile 和 FastAPI 代码。
- 在 `docker-compose.yml` 中使用 `profiles [ocr]`，保证默认启动时不拉取这 2GB 的巨型镜像。
- 使用 `paddlepaddle==2.6.2` 和 `paddleocr==2.8.1`，并挂载了 `paddle_models` 数据卷，避免重复下载模型。

#### 2、主后端插件（ocr_plugin）
- 新建 `ocr_plugin`。
- 通过 `httpx.AsyncClient` 向内部微服务发起请求。在 Docker 网络下，直接用容器名 `httpocr-service8001ocr` 通信。
- 将返回的坐标和文本合并成一大段字符串，封装成前端需要的 `ParsedProblem` 格式。

#### 3、前端交互（OcrUploader）
- 开发 `OcrUploader.vue`，使用原生 `input type=file capture=environment` 在移动端直接拉起相机，无需额外原生插件。
- 用户上传图片后，展示 Loading 动画，后端返回后展示勾选列表，最后调用批量导入 API 落库。

### 三、踩坑记录

#### 1、基础镜像缺失底层 C++ 库
现象：容器不断处于 `Restarting` 状态，报错 `ImportError libgomp.so.1 cannot open shared object file`。
原因：`python3.10-slim` 极度精简，缺少 PaddlePaddle 运算所需的 OpenMP 依赖。
解决：在 Dockerfile 的 `apt-get install` 中追加 `libgomp1`。

#### 2、Docker 构建耗时极长
现象：`docker compose --profile ocr build ocr-service` 执行了将近 20 分钟。
原因：PaddlePaddle 包含大量科学计算依赖（numpy、opencv 等），下载和编译极慢。
解决：属于正常现象。通过 `profiles` 机制，只有显式指定时才构建，主程序用户完全无感。

#### 3、新建后端文件未生效
现象：日志里 `plugins` 列表死活找不到 `ocr_plugin`。
解决：Docker 环境使用的是 `build` 复制的快照，不是源码挂载。新建文件后，必须重新执行 `docker compose build backend`，然后 `up -d` 才能加载。

### 四、遗留问题（待 Day 51 解决）
1. 题型硬编码：目前识别结果统一按 `type algorithm` 写入，数学题或证明题分类不准。
2. LaTeX 渲染：PaddleOCR 返回的是纯文本，前端 `marked` 无法将其识别为公式，需要增加定界符（`$$...$$`）或升级渲染引擎。
