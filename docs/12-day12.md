### 三、编写 backend/Dockerfile

在 `backend/` 目录下新建 `Dockerfile`：

```dockerfile
FROM python:3.11-slim

WORKDIR /app

ENV TZ=Asia/Shanghai

RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt \
    -i https://pypi.tuna.tsinghua.edu.cn/simple

COPY . .

RUN mkdir -p /app/uploads

EXPOSE 8000

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

#### 逐段说明

| 指令 | 作用 |
|---|---|
| `FROM python:3.11-slim` | 基础镜像，轻量版 Python 3.11 |
| `WORKDIR /app` | 容器内工作目录 |
| `ENV TZ=Asia/Shanghai` | 设置时区 |
| `apt-get install gcc` | asyncpg 编译依赖 |
| `COPY requirements.txt .` | 先复制依赖清单 |
| `pip install` | 安装依赖 |
| `COPY . .` | 复制源码 |
| `mkdir -p /app/uploads` | 创建上传目录（运行时被挂载卷覆盖） |
| `CMD [...]` | 启动 uvicorn |

#### 为什么要分两步 COPY

Docker 每行是一条镜像层，构建时缓存。若只改源码，`requirements.txt` 未变，pip 安装层会复用缓存。若一次性 `COPY . .` 再 `pip install`，任何源码改动都会导致 pip 重新安装。

### 五、更新 docker-compose.yml

整体替换项目根目录的 `docker-compose.yml`：

```yaml
services:
  postgres:
    image: postgres:15-alpine
    environment:
      POSTGRES_USER: oj
      POSTGRES_PASSWORD: oj_password
      POSTGRES_DB: oj_platform
    ports:
      - "5432:5432"
    volumes:
      - pg_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U oj -d oj_platform"]
      interval: 5s
      timeout: 3s
      retries: 5

  backend:
    build: ./backend
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql+asyncpg://oj:oj_password@postgres:5432/oj_platform
      ADMIN_KEY: ${ADMIN_KEY:-admin-key-change-me}
    volumes:
      - ./backend/uploads:/app/uploads
    depends_on:
      postgres:
        condition: service_healthy
    restart: unless-stopped

volumes:
  pg_data:
```

#### 关键点

| 配置 | 说明 |
|---|---|
| `build: ./backend` | 用 backend 目录的 Dockerfile 构建 |
| `@postgres` | 容器间通过服务名访问，不能用 localhost |
| `volumes: ./backend/uploads:/app/uploads` | 宿主与容器共享上传目录 |
| `healthcheck` | 数据库健康检查 |
| `condition: service_healthy` | 等数据库就绪后再启动后端 |
| `restart: unless-stopped` | 异常退出时自动重启 |

#### 为什么数据库地址是 postgres 而不是 localhost

Docker Compose 会为所有服务创建默认网络，服务名会被解析为容器 IP。后端容器内访问 `postgres:5432` 即可连上数据库。若写 `localhost:5432`，会连到后端容器自己。

### 八、关键坑：容器内代码是构建时的快照

**这是本项目最大的坑之一。**

`docker compose restart backend` **只重启进程，不更新代码**。

- 容器内的代码是**构建镜像时**复制的
- 修改宿主机上的源码后，容器里的代码不变
- `restart` 无效，必须 `build` 重建

#### 两种解决方案

**方案 A：重建镜像**（每次改代码都要做）

```
docker compose build --no-cache backend
docker compose up -d backend
```

`--no-cache` 忽略构建缓存，确保拿到最新代码。

**方案 B：挂载源码目录**（开发时推荐）

在 `docker-compose.yml` 的 backend 服务下加：

```yaml
volumes:
  - ./backend/uploads:/app/uploads
  - ./backend/app:/app/app          # 挂载源码
```

改代码后只需 `docker compose restart backend`，无需重建。

#### 判断当前容器里跑的是什么代码

```
docker exec -it oj-platform-backend-1 cat /app/app/plugins/problem_plugin/image_api.py
```

对照宿主机上的 `backend/app/plugins/problem_plugin/image_api.py`，若不一致，说明容器里是旧代码。

### 十一、Nginx 部署配置

#### 1、创建 deploy/nginx.conf

```nginx
server {
    listen 80;
    server_name your-domain.com;

    root /var/www/oj-platform;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://localhost:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 10M;
    }

    location ~* \.(jpg|jpeg|png|webp|gif|ico|css|js|woff2?)$ {
        expires 7d;
        add_header Cache-Control "public, immutable";
    }

    gzip on;
    gzip_types text/plain text/css application/json application/javascript text/xml application/xml;
    gzip_min_length 1000;
}
```

#### 2、关键配置

| 配置 | 作用 |
|---|---|
| `try_files $uri $uri/ /index.html` | history 模式回退 |
| `location /api/` | 转发 API 到后端 |
| `proxy_set_header` | 保留客户端信息 |
| `expires 7d` | 静态资源缓存 |
| `gzip on` | 压缩传输 |

### 十二、Docker 部署的图片路径问题

#### 1、现象

本地开发时用 uvicorn 上传的图片，`file_path` 记录为 Windows 绝对路径（如 `E:\github_project\...\uploads\2026/09\xxx.png`）。改用容器运行后端后，容器内看不到该路径，返回 `{"detail":"图片文件已丢失"}`。

#### 2、三种 file_path 格式

| 格式 | 示例 | 适用环境 |
|---|---|---|
| 绝对路径 | `E:\...\uploads\...\xxx.png` | 本地 uvicorn |
| 容器绝对路径 | `/app/uploads/2026/09/xxx.png` | 容器 |
| 相对路径 / 纯文件名 | `2026/09/xxx.png` 或 `xxx.png` | 通用 |

#### 3、兼容方案：改造 get_image 函数

```python
@router.get("/images/{image_id}")
async def get_image(image_id: int, db: AsyncSession = Depends(get_db)):
    image = await db.get(Image, image_id)
    if not image:
        raise HTTPException(status_code=404, detail="图片不存在")

    path = image.file_path

    # 1. 绝对路径：直接使用
    if os.path.isabs(path) and os.path.exists(path):
        return FileResponse(path, media_type=image.mime_type)

    # 2. 相对路径拼接 UPLOAD_DIR
    candidate = os.path.join(settings.UPLOAD_DIR, path)
    if os.path.exists(candidate):
        return FileResponse(candidate, media_type=image.mime_type)

    # 3. 只存文件名时，扫描 uploads 子目录
    for root, dirs, files in os.walk(settings.UPLOAD_DIR):
        if path in files:
            full = os.path.join(root, path)
            return FileResponse(full, media_type=image.mime_type)

    raise HTTPException(status_code=404, detail="图片文件已丢失")
```

#### 4、修改上传接口：只存文件名

```python
# 只存文件名（相对路径）
image = Image(
    problem_id=problem_id,
    file_name=file.filename,
    file_path=unique_name,   # 只存文件名
    file_size=len(content),
    mime_type=file.content_type,
    upload_by="admin",
)
```

#### 5、通用经验

- **开发与部署切换时，路径策略必须统一**
- **优先用相对路径存储**，读取时拼接基准目录
- **写兼容函数处理历史数据**，不要假设数据库里只有一种格式

### 十三、常见问题与排查

#### 1、docker compose up 报端口被占用

现象：

```
Error starting userland proxy: listen tcp4 0.0.0.0:5432: bind: address already in use
```

排查：

```
netstat -ano | findstr :5432
netstat -ano | findstr :8000
```

找到进程 PID，结束后再启动，或修改端口映射。

#### 2、后端连不上数据库

**检查 1**：`DATABASE_URL` 中的 host 必须是服务名 `postgres`，不能是 `localhost`。

**检查 2**：`depends_on.condition` 配置。

**检查 3**：查看后端日志：

```
docker compose logs backend
```

#### 3、alembic upgrade head 在容器内报错

常见原因：

- `alembic.ini` 的 `script_location` 不正确
- 容器内 `app.models` 导入失败
- 数据库连接失败

排查：

```
docker compose exec backend alembic current
docker compose exec backend alembic history
```

#### 4、图片上传后丢失

检查 `docker-compose.yml` 的 volumes：

```yaml
volumes:
  - ./backend/uploads:/app/uploads
```

宿主机和容器对比：

```
dir E:\github_project\oj-platform\backend\uploads\2026\09
docker compose exec backend ls /app/uploads/2026/09
```

#### 5、修改代码后容器未更新

容器是快照。三种处理方式：

| 方式 | 命令 | 生效速度 |
|---|---|---|
| 重建镜像 | `docker compose up -d --build backend` | 慢（几分钟） |
| 强制重建 | `docker compose build --no-cache backend` | 更慢 |
| 挂载源码 | volumes 加 `- ./backend/app:/app/app` | 最快 |

#### 6、数据卷冲突

如需全新数据库：

```
docker compose down -v
docker compose up -d --build
docker compose exec backend alembic upgrade head
```

#### 7、Windows 路径挂载

用相对路径 `./backend/uploads`，不要硬编码绝对路径。

#### 8、容器时区

在 Dockerfile 中加 `ENV TZ=Asia/Shanghai`，或在 compose 的 `environment` 中设置。

### 十四、开发与部署的三种模式

| 场景 | 数据库 | 后端 | 前端 |
|---|---|---|---|
| 本地开发 | Docker postgres | 本地 uvicorn --reload | npm run dev |
| 完全容器化 | Docker postgres | Docker backend | npm run dev / preview |
| 生产部署 | Docker postgres | Docker backend | Nginx 静态 |

**本地开发**：改动立即生效，无需重建镜像，是日常使用最频繁的模式。

**完全容器化**：用于验证 Dockerfile 和 compose 配置，接近生产。

**生产部署**：加 Nginx 反向代理、HTTPS、域名、日志收集。

### 十七、常见问题速查

| 现象 | 原因 | 解决 |
|---|---|---|
| 构建时 pip 失败 | 网络问题 | 使用清华镜像或重试 |
| 后端连不上 postgres | DATABASE_URL 用了 localhost | 改为服务名 postgres |
| 后端启动顺序错误 | 未加 depends_on | 加 healthcheck 和 depends_on |
| 容器重启后数据丢失 | 卷未正确配置 | 检查 volumes |
| 前端请求 404 | 后端未启动 | `docker compose logs backend` |
| 修改代码后容器未变 | 容器是快照 | 重新 `--build` 或挂载源码 |
| 数据库要重置 | 卷缓存 | `docker compose down -v` |
| 时间戳偏移 | 时区未设置 | 加 `TZ=Asia/Shanghai` |
| Windows 路径挂载失败 | 路径格式错误 | 用相对路径 `./backend/uploads` |
| 图片 404 | 路径格式不匹配 | 改造 get_image 兼容多种格式 |
| 容器内代码是旧版 | 未 rebuild | `docker compose build --no-cache backend` |
