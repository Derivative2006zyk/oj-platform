# 第 70 天：冲突合并策略（LWW + 字段级合并）

### 一、今日目标

Day 69 将断网写操作接入队列，但回放时遇到 409 只能标记为 `conflict` 并停止；用户既不知道哪个字段冲突，也无法继续保存。乐观锁已实现，但缺少合并策略。

今日三个目标：

1. **后端补充冲突详情**：409 响应返回服务端快照与版本号，为前端提供对比依据
2. **前端字段级合并**：以加载时的基线做三路合并；双方改动不同字段时自动合并
3. **冲突人工处理**：提供保留本地、保留服务器、逐字段选择三种方式，并接入离线队列

### 二、核心实现

#### 1、后端返回结构化冲突详情

原来只返回一句 `detail`，前端无法判断冲突范围。改为返回结构化对象：

```python
if problem.version != data.version:
    raise HTTPException(
        status_code=409,
        detail={
            "message": "该题目已被其他设备修改",
            "conflict": {
                "problem_id": problem.id,
                "client_version": data.version,
                "server_version": problem.version,
                "server": _snapshot_problem(problem),
            },
        },
    )
```

`_snapshot_problem` 按 `ProblemUpdate` 的字段对齐输出，前端可直接用来回填或合并：

```python
def _snapshot_problem(problem: Problem) -> dict:
    return {
        "title": problem.title,
        "category_id": problem.category_id,
        "bank_id": problem.bank_id,
        "paper_id": problem.paper_id,
        "type": problem.type,
        "difficulty": problem.difficulty,
        "description": problem.description,
        "answer": problem.answer,
        "explanation": problem.explanation,
        "tags": problem.tags or [],
        "options": problem.options,
        "blanks": problem.blanks,
        "version": problem.version,
    }
```

**未返回 `server_updated_at`**：模型的 `updated_at` 只有 `server_default` 没有 `onupdate`，ORM 更新后不会刷新，取值始终是创建时间；返回它会让用户误以为有人在很久以前修改过。

#### 2、三路合并的正确基准

字段级合并的关键在于**比较基准必须是加载时的快照**，而不是直接拿本地和服务器比较。

```ts
export function tryMerge(local, base, server): MergeResult {
  if (!base) return { ok: false, overlap: [...MERGEABLE_FIELDS], ... }

  const localChanged = MERGEABLE_FIELDS.filter(f => !isEqual(local[f], base[f]))
  const serverChanged = MERGEABLE_FIELDS.filter(f => !isEqual(server[f], base[f]))

  const overlap = localChanged.filter(f => serverChanged.includes(f))
  if (overlap.length > 0) return { ok: false, overlap, localChanged, serverChanged }

  const merged = { ...server }
  localChanged.forEach(f => { merged[f] = local[f] })
  merged.version = server.version
  return { ok: true, merged, overlap: [], localChanged, serverChanged }
}
```

判定逻辑：

| 情况 | 结果 |
|---|---|
| 只有本地改了 | 用本地的 |
| 只有服务器改了 | 用服务器的 |
| 两边都改了同一字段 | 冲突，需人工选择 |
| 两边都没改 | 用服务器的 |

基线缺失时（例如首次加载就走缓存）无法判断来源，一律视为冲突，进入人工模式。

#### 3、比较函数的规范化

数组与对象直接 `JSON.stringify` 会受键顺序影响，需要先排序：

```ts
function sortKeys(obj: Record<string, any>): Record<string, any> {
  return Object.keys(obj).sort().reduce((acc, k) => { acc[k] = obj[k]; return acc }, {})
}

export function normalize(value: any): string {
  if (value === null || value === undefined) return ''
  if (Array.isArray(value)) {
    return JSON.stringify(value.map(v => (v && typeof v === 'object' ? sortKeys(v) : v)))
  }
  if (typeof value === 'object') return JSON.stringify(sortKeys(value))
  return String(value)
}
```

只对对象键排序，**不排序数组元素**，因为选项顺序变化本身就应该算一次修改。

#### 4、冲突弹窗的三种处理

| 模式 | 行为 | 适用 |
|---|---|---|
| 保留服务器 | 回填服务端快照，丢弃本地 | 本地改错，或对方版本更优 |
| 自动合并 | 只对不重叠字段调用 `tryMerge` | 双方改动无交集 |
| 按选择合并 | 逐字段选择，合成后再提交 | 有重叠字段 |

弹窗先判断 `mergeable`，可合并时只显示「自动合并」，否则显示逐字段对比与「按选择合并」。

所有合并路径提交前都会把 `version` 覆写为 `server.version`，这是保存成功的前提。

#### 5、队列冲突的人工解决

```ts
export function resolveConflict(id: string, resolution: 'local' | 'server', serverVersion?: number) {
  const action = getQueue().find(a => a.id === id)
  if (!action) return

  if (resolution === 'server') {
    removeActionFromQueue(id)
    return
  }

  updateAction(id, {
    status: 'pending',
    attempts: 0,
    lastError: undefined,
    data: { ...(action.data || {}), version: serverVersion ?? action.data?.version ?? 1 },
  })

  processQueue()
}
```

保留本地时，用服务端最新版本号重写 `data` 后再入队，避免再次 409 循环。

### 三、踩坑记录

#### 1、模板未挂载弹窗导致冲突时界面无反应

**现象**：`ConflictDialog` 已 import，`conflictVisible` 也置为 `true`，但用户点保存后什么都不发生。
**原因**：模板里漏了 `<ConflictDialog ... />` 标签，组件被导入但从未渲染。
**解决**：在模板末尾补上组件标签，并同时传入 `buildSubmitData()` 作为本地快照。

#### 2、`cancel` 方法缺失

**现象**：模板第 186 行调用了 `cancel`，脚本区没有定义。
**原因**：该函数在更早的重构中丢失。
**解决**：补上 `function cancel() { router.push('/') }`。

#### 3、答案回填后污染基线

**现象**：编辑页刚加载完，什么都没动，点保存就报冲突。
**原因**：`applyDetailToForm` 在 `getProblemAnswer` 之前执行，基线里 `answer` 是空的；答案回填后本地 `answer` 非空，被判定为「本地改过」。
**解决**：答案回填后同步更新 `baseSnapshot` 的 `answer` 与 `explanation`，缓存分支同样处理。

#### 4、`server_updated_at` 取值失真

**现象**：计划返回服务端最后修改时间供对比，但拿到的是创建时间。
**原因**：`updated_at` 字段只有 `server_default=func.now()`，无 `onupdate`，ORM 层的 `setattr` 不会触发时间刷新。
**解决**：本轮不返回该字段；模型层补 `onupdate` 作为后续改进项。

#### 5、数组比较受键顺序影响

**现象**：双方都没动 `options`，却被判定冲突。
**原因**：对象键顺序不同导致 `JSON.stringify` 结果不同。
**解决**：`normalize` 中对对象做键排序，数组保持原序。
