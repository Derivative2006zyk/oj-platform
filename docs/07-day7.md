### 一、测试框架选型

| 工具 | 职责 |
|---|---|
| pytest | 测试运行器 |
| pytest-asyncio | 异步测试支持 |
| httpx.AsyncClient | 异步 HTTP 客户端 |

#### 对比测试方式

| 方式 | 速度 | 依赖 |
|---|---|---|
| ASGITransport | 快 | 无（不需要启动 uvicorn） |
| requests + uvicorn | 慢 | 需启动服务器 |
| Playwright/Selenium | 最慢 | 需浏览器 |

#### 2、conftest.py 的实现
```python
# backend/tests/conftest.py
import os
os.environ["TESTING"] = "1"
os.environ["DATABASE_URL"] = (
    os.environ.get("TEST_DATABASE_URL")
    or "postgresql+asyncpg://oj:oj_password@localhost:5432/oj_platform_test"
)

import pytest
from httpx import AsyncClient, ASGITransport
from app.main import app
from app.database import Base, engine, async_session
from app.models.category import Category

@pytest.fixture(autouse=True)
async def setup_database():
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.drop_all)
        await conn.run_sync(Base.metadata.create_all)

    async with async_session() as session:
        session.add_all([
            Category(name="算法", sort_order=1),
            Category(name="数学", sort_order=2),
            Category(name="物理", sort_order=3),
            Category(name="英语", sort_order=4),
            Category(name="其他", sort_order=99),
        ])
        await session.commit()

    yield

    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.drop_all)

@pytest.fixture
async def client():
    transport = ASGITransport(app=app)
    async with AsyncClient(transport=transport, base_url="http://test") as c:
        yield c
```

#### 3、原理分析

| 步骤 | 说明 |
|---|---|
| 首先设置环境变量 | 必须在导入 app 前，因为 config 在导入时读取环境变量 |
| autouse=True | 每个测试函数自动执行 setup/teardown |
| drop_all + create_all | 每次测试前清空表结构，保证干净 |
| 预置 5 条分类 | 使后续测试有分类可用 |
| yield | 前后分为 setup 和 teardown |

#### 4、环境变量必须在导入前设置的原因
```python
os.environ["DATABASE_URL"] = "..."
from app.main import app  # 此处会触发 app.core.config 的加载
```
`app.core.config` 中的 Settings 类在模块导入时实例化，读取环境变量。若在导入 app 之后再设置环境变量，Settings 已使用旧值。

### 六、问题排查方法论

#### 1、排查流程
```
1. 打印真实响应
   → 加入 print(res.status_code, res.text) 或使用 -s 参数

2. 打印已注册路由
   → python -c "from app.main import app; [print(r.path) for r in app.routes]"

3. 检查数据库状态
   → docker exec -it 容器名 psql -U oj -d 库名 -c "SELECT ..."

4. 检查服务层逻辑
   → 单独测试 service 函数

5. 检查模型定义
   → 打印 Base.metadata.sorted_tables 查看列
```

#### 2、诊断测试的写法
```python
@pytest.mark.asyncio
async def test_debug_pipeline(client):
    res = await client.get("/api/categories")
    print(f"[1] GET /api/categories -> {res.status_code} | {res.text[:200]}")

    payload = {...}
    res = await client.post("/api/admin/problems", json=payload, headers=ADMIN_HEADERS)
    print(f"[2] POST /api/admin/problems -> {res.status_code} | {res.text[:200]}")
```

运行：`pytest tests/test_debug.py -v -s`。

#### 3、路由未匹配的判别方法
FastAPI 默认 404 返回 `{"detail": "Not Found"}`（首字母大写）。自定义 404 通常返回自定义消息。

若看到 `"Not Found"`（无自定义），说明路由未匹配；若看到自定义消息，说明路由匹配但服务层抛出了 404。

### 七、跨事件循环连接池问题

#### 1、现象
测试用例在第二个之后开始报 `Event loop is closed` 或 `another operation is in progress`。

#### 2、原因
pytest-asyncio 每个测试函数创建独立 event loop。SQLAlchemy 连接池的旧连接绑定到已关闭的 loop，复用时报错。

#### 3、解决
在测试环境使用 NullPool（每次请求新建连接），通过 TESTING 环境变量切换。

```python
# backend/app/database.py
import os
from sqlalchemy.pool import NullPool

_engine_kwargs = {"echo": False}
if os.environ.get("TESTING") == "1":
    _engine_kwargs["poolclass"] = NullPool

engine = create_async_engine(settings.DATABASE_URL, **_engine_kwargs)
```

#### 4、连接池的通用选择

| 池类型 | 适用场景 |
|---|---|
| QueuePool（默认） | 一般场景 |
| NullPool | 测试、Lambda 等短生命周期 |
| AsyncAdaptedQueuePool | 异步应用 |
| StaticPool | 单元测试 |

### 九、测试数据管理原则

- 每个测试独立数据，不依赖前一个测试
- 使用 drop_all + create_all 保证初始状态
- 预置必要的基础数据（如分类）
- 使用辅助函数生成测试数据，减少重复

### 十、注意事项

#### 1、测试数据库必须手动创建
- `CREATE DATABASE oj_platform_test;` 只需执行一次。
- 若数据库不存在，测试会在连接时报 `InvalidCatalogNameError`。

#### 2、环境变量设置必须在导入 app 之前
- `os.environ["DATABASE_URL"] = "..."` 必须放在 `from app.main import app` 之前。
- 若顺序颠倒，Settings 会使用默认 URL，测试会污染开发数据库。

#### 3、asyncio_default_test_loop_scope 不被低版本识别
- pytest-asyncio 0.24 不支持 `asyncio_default_test_loop_scope` 配置项。
- 若在 pytest.ini 中配置了该项，会报 `PytestConfigWarning: Unknown config option`。
- 解决：删除该项配置。

#### 4、asyncio_default_fixture_loop_scope 可选
- 若出现 `PytestDeprecationWarning`，可加上 `asyncio_default_fixture_loop_scope = function` 消除警告。
- 不加不影响功能。

#### 5、跨事件循环连接池问题
- pytest-asyncio 每个测试函数一个 event loop。
- SQLAlchemy 连接池缓存的连接绑定到旧 loop，复用时报错。
- 解决：测试环境用 NullPool。

#### 6、engine.dispose() 可能引发新问题
- 在 fixture 里调用 `await engine.dispose()` 看似能重置连接池，但可能破坏其他测试。
- 推荐方案：用 NullPool，不需要手动 dispose。

#### 7、测试用例的独立性
- 每个测试不应依赖前一个测试的数据。
- `drop_all + create_all` 保证每个测试初始状态干净。
- 若某个测试失败，不影响其他测试。

#### 8、断言失败时看 traceback 的最后几行
- pytest 的报错信息通常在前面显示"上下文"，最后几行才是根因。
- 重点看 `E   assert ...` 那一行和它上面的 `res.text` 内容。

#### 9、pytest -s 会显示所有 print
- 加了 `-s` 参数，pytest 不会捕获 stdout，print 会直接输出到终端。
- 排查问题时非常有用。

#### 10、pytest -x 遇到第一个失败立即停止
- 加快调试循环。
- 项目全部通过后不需要加。

#### 11、诊断文件用完要删除
- 诊断文件中通常有 `assert False`，若保留会污染测试结果。
- 确认问题解决后立即 `del tests/test_debug.py`。

#### 12、临时文件的 Git 处理
- 诊断文件 `test_debug.py` 属于临时文件，不应提交到 Git。
- 删除后再 `git add .`。
