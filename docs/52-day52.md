# 第 52 天：插件微服务自动化编排

## 一、今日目标

Day 51 结束时，`ocr-service` 这个 GPU 重型微服务是硬编码在项目根 `docker-compose.yml` 里的，靠 `profiles: ["ocr"]` 手动 `docker compose --profile ocr up -d` 才能拉起，**完全背离了「插件市场一键安装」的产品承诺**。

Day 52 的核心任务是把重型微服务「关进插件的笼子里」：

1. 根 `docker-compose.yml` 彻底移除 `ocr-service` 服务。
2. 微服务编排下沉到插件包内部的 `docker-compose.yml`。
3. 主后端在插件安装时通过 `docker compose` 拉起微服务，卸载时销毁。
4. 前端补上「卸载」按钮，形成「安装 → 使用 → 卸载 → 复装」完整闭环。
5. 修复「内置 `ocr_plugin` 与外部 `ocr_plugin` 同名冲突」的架构隐患。

## 二、架构设计与设计决策

### 2.1 整体编排流程

```
用户点击「一键安装」
    ↓
POST /api/admin/market/install { download_url }
    ↓
┌─────────────────────────────────────────────────────┐
│ 后端 install_plugin 五阶段：                          │
│  1. 下载 .ojplugin（ZIP）到临时文件                    │
│  2. 读 manifest.json 拿 name，解压到                 │
│     /app/plugins_installed/{name}/                   │
│  3. pip install -r backend/requirements.txt           │
│  4. registry.reload_external() 动态导入插件类          │
│  5. plugin.on_install(plugin_dir)                    │
│     → docker compose -p oj-plugin-{name} \           │
│       -f .../docker-compose.yml \                    │
│       up -d --wait                                   │
└─────────────────────────────────────────────────────┘
    ↓
前端轮询 /api/plugins/ui 直到健康
    ↓
Tauri: invoke('restart_backend_cmd') 重启主后端
Web:   弹窗提示手动 docker restart
    ↓
重启后 main.py 启动时：
  discover_external → _build_instances → collect_routers
  → app.include_router(ocr 路由)
    ↓
导航栏「拍照录题」出现
```

### 2.2 关键设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 微服务启动命令位置 | 插件包内的 `docker-compose.yml` | 插件自包含，主程序不感知微服务细节 |
| 容器命名 | `oj-plugin-{name}-service` | 命名空间隔离，避免与主程序容器冲突 |
| 网络 | 复用外部网络 `oj-platform_default` | 主 backend 与微服务在同一 Docker 网络，直接通过容器名访问 |
| 端口暴露 | **不映射**宿主机端口（`ports: []`） | 避免宿主机端口冲突，插件微服务只在 Docker 内网可达 |
| 健康检查 | FastAPI 默认的 `/openapi.json` | 不依赖微服务自己实现 `/health`，通用性极强 |
| 卸载策略 | `docker compose down`（不删镜像） | 镜像保留 → 下次安装秒级，仅 Day 53 提供"彻底卸载"选项 |
| 卸载后路由 | 保留到下次重启消失 | FastAPI 运行时无法删除 `app.include_router` 添加的路由 |
| Compose 二进制 | 从 Dockerfile 持久化 | 每次 `docker compose build backend` 重建容器会丢 `docker cp` 的临时文件 |

### 2.3 为什么不用 Docker-in-Docker（DinD）

考虑过三种微服务编排方案：

| 方案 | 优点 | 缺点 | 采用 |
|---|---|---|---|
| **Docker Socket 挂载**（DooD） | 简单，无额外容器 | 有权限风险 | ✅ |
| Docker-in-Docker（DinD） | 完全隔离 | 镜像体积 +500MB，GPU 直通复杂 | ❌ |
| 手动 ssh 到宿主 | 无权限问题 | 脆弱、不可移植 | ❌ |

最终选择 DooD。通过 `/var/run/docker.sock` 挂载，加上 `docker compose` 二进制注入，让 backend 容器具备与宿主机等同的编排能力。**风险控制**：`docker.sock` 只在 backend/worker 容器内可见；`entrypoint.sh` 里加 `command -v docker` 检查；插件 `docker-compose.yml` 不带 `ports` 映射。

## 三、核心实现

### 3.1 Plugin 基类扩展（`backend/app/core/plugin_base.py`）

```python
class Plugin(ABC):
    name: str = ""
    version: str = "0.0.0"
    dependencies: List[str] = []

    @abstractmethod
    async def on_load(self) -> None: ...

    async def on_enable(self) -> None: pass
    async def on_disable(self) -> None: pass
    async def on_unload(self) -> None: pass

    # 【Day 52 新增】
    async def on_install(self, plugin_dir: Path) -> None:
        """插件安装时调用（可选，用于拉起微服务）"""
        pass

    async def on_uninstall(self, plugin_dir: Path) -> None:
        """插件卸载前调用（可选，用于销毁微服务）"""
        pass

    def get_routers(self) -> List[APIRouter]:
        return []
```

**设计哲学**：生命周期钩子默认空实现，避免每个插件都要写 `pass`。只有 OCR、AI 这种带微服务的重型插件才需要重写 `on_install`/`on_uninstall`。这就是**「按需覆写」**原则。

### 3.2 PluginRegistry 增强（`backend/app/core/plugin_registry.py`）

新增三个关键方法和一个常量：

```python
PLUGINS_INSTALLED_DIR = Path("/app/plugins_installed")

class PluginRegistry:
    def reload_external(self, plugin_dir: str) -> None:
        """重新扫描外部插件目录，将新插件类注册进来并实例化"""
        self.discover_external(plugin_dir)
        self._build_instances()

    async def install_plugin(self, name: str) -> None:
        """插件文件已落盘后调用：重新扫描 → 实例化 → 触发 on_install"""
        self.reload_external(str(PLUGINS_INSTALLED_DIR))
        plugin = self._plugins.get(name)
        if plugin is None:
            raise RuntimeError(f"Plugin class for '{name}' not found after reload")
        plugin_dir = PLUGINS_INSTALLED_DIR / name
        await plugin.on_install(plugin_dir)

    async def uninstall_plugin(self, name: str) -> None:
        """触发 on_uninstall + 从内存中移除 + 兜底 compose down"""
        plugin = self._plugins.get(name)
        plugin_dir = PLUGINS_INSTALLED_DIR / name
        if plugin is not None:
            try:
                await plugin.on_uninstall(plugin_dir)
            finally:
                await plugin.on_unload()
                self._plugins.pop(name, None)

        # 兜底：即使插件未加载，也尝试销毁可能的容器
        compose_file = plugin_dir / "docker-compose.yml"
        if compose_file.exists():
            await _run_compose_down(name, compose_file)
```

**关键改进**：`_build_instances()` 现在有幂等性保护：

```python
def _build_instances(self) -> None:
    for cls in _plugin_classes:
        try:
            instance = cls()
            if instance.name not in self._plugins:  # 幂等
                self._plugins[instance.name] = instance
        except Exception as e:
            print(f"[PluginRegistry] Error instantiating {cls.__name__}: {e}")
```

`_run_compose_down` 是一个独立异步函数，直接 `subprocess` 调用 `docker compose down --remove-orphans`，作为卸载失败时的兜底。

### 3.3 backend 容器获得 Docker Compose 能力

**这是今天踩得最深的坑，也是必须方案化的关键部分。**

#### 3.3.1 为什么必须持久化到 Dockerfile

`docker cp docker-compose-linux oj-platform-backend-1:/usr/local/libexec/...` 只对**当前运行容器**生效。一旦 `docker compose build backend` 重建镜像，整个容器的可写层就会被新镜像替换，临时拷贝的 compose 二进制**凭空消失**。

今天经历了这个循环：
1. `docker cp` 注入 compose → `docker compose version` 成功
2. `docker compose build backend worker` 重建镜像 → compose 又没了
3. 又得 `docker cp` → 又进循环

**教训**：**任何需要长期存在于容器内的文件，必须通过 `Dockerfile` 的 `COPY` 指令注入镜像，不能依赖 `docker cp` 到运行中的容器。**

#### 3.3.2 Dockerfile 的精确改动

```dockerfile
FROM python:3.11-slim
WORKDIR /app

RUN sed -i ... && apt-get install ... 
COPY requirements.txt .
RUN pip install ...

COPY . .
RUN mkdir -p /app/uploads

# 已有的 docker CLI
COPY --from=docker:27-cli /usr/local/bin/docker /usr/local/bin/docker

# 【Day 52 新增】Docker Compose 插件
COPY docker-compose-linux /usr/local/libexec/docker/cli-plugins/docker-compose
RUN chmod +x /usr/local/libexec/docker/cli-plugins/docker-compose \
    && rm -f /app/docker-compose-linux

RUN chmod +x /app/entrypoint.sh
ENTRYPOINT ["/app/entrypoint.sh"]
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**`COPY` 位置的玄机**：
- `COPY docker-compose-linux ...` 放在 `COPY --from=docker:27-cli` 之后，`COPY . .` 之后
- 因为 `.dockerignore` 没有排除 `docker-compose-linux`，`COPY . .` 会先把 63MB 二进制拷进 `/app/`（多余的）
- 所以 `RUN rm -f /app/docker-compose-linux` 把 `/app/` 下的多余副本删掉，节省 63MB 镜像体积
- 最终二进制只在 `/usr/local/libexec/docker/cli-plugins/docker-compose`，这是 Docker CLI 查找**插件**（`docker compose xxx`）的标准路径

**构建成本**：`docker compose build backend worker` 总耗时 **13 秒**，因为 `pip install` 层全部 `CACHED`，只有 `COPY . .` 和之后三层是新跑的。

#### 3.3.3 Compose 二进制的下载来源

Docker Hub 拉镜像 `docker/compose:2.29.7` 在国内网络下 **403 Forbidden**（加速器 `docker.xuanyuan.me` 也不可用），只能走 GitHub Release + `ghfast.top` 代理：

```cmd
curl -L -o docker-compose-linux ^
  "https://ghfast.top/https://github.com/docker/compose/releases/download/v2.29.7/docker-compose-linux-x86_64"
```

63.7 MB，11 秒下载完成。

**为什么不用 `docker/compose` 镜像**：Docker Hub 拉不动；**为什么不用 apt install docker-compose**：Ubuntu 22.04 源里的是 1.x 版本，不支持 `docker compose` 子命令；**为什么不用 pip install docker-compose**：1.x 版本，同样不支持。

**GitHub Release 是唯一可靠来源。**

### 3.4 OcrPlugin 微服务编排（`backend/app/plugins/ocr_plugin/__init__.py`）

```python
OCR_SERVICE_CONTAINER = "oj-plugin-ocr_plugin-service"
OCR_SERVICE_URL = f"http://{OCR_SERVICE_CONTAINER}:8001"
# 用 FastAPI 默认暴露的 /openapi.json 做健康探测
OCR_SERVICE_HEALTH = f"{OCR_SERVICE_URL}/openapi.json"


@register_plugin
class OcrPlugin(Plugin):
    name = "ocr_plugin"
    version = "0.3.0"
    dependencies = ["problem_plugin"]

    async def on_load(self) -> None:
        # 探测一次，失败也不影响主程序启动
        try:
            async with httpx.AsyncClient(timeout=3.0) as client:
                r = await client.get(OCR_SERVICE_HEALTH)
                if r.status_code == 200:
                    print(f"[OcrPlugin] OCR service is healthy")
                else:
                    print(f"[OcrPlugin] OCR service returned {r.status_code}")
        except Exception as e:
            print(f"[OcrPlugin] OCR service not reachable: {e}")

    async def on_install(self, plugin_dir: Path) -> None:
        compose_file = plugin_dir / "docker-compose.yml"
        if not compose_file.exists():
            return

        project_name = f"oj-plugin-{self.name}"
        proc = await asyncio.create_subprocess_exec(
            "docker", "compose",
            "-p", project_name,
            "-f", str(compose_file),
            "up", "-d", "--wait",
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE,
        )
        stdout, stderr = await proc.communicate()

        if proc.returncode != 0:
            print(f"[OcrPlugin] compose up failed:\nSTDOUT:\n{stdout.decode()[-2000:]}\nSTDERR:\n{stderr.decode()[-2000:]}")
            raise RuntimeError(f"docker compose up failed with code {proc.returncode}")

        # 保险：--wait 已通过，额外做一次 HTTP 探测
        for i in range(30):
            try:
                async with httpx.AsyncClient(timeout=2.0) as client:
                    r = await client.get(OCR_SERVICE_HEALTH)
                    if r.status_code == 200:
                        print(f"[OcrPlugin] Health check passed")
                        return
            except Exception:
                pass
            await asyncio.sleep(1)

        raise RuntimeError("OCR service health check timeout (30s)")

    async def on_uninstall(self, plugin_dir: Path) -> None:
        compose_file = plugin_dir / "docker-compose.yml"
        if not compose_file.exists():
            return
        proc = await asyncio.create_subprocess_exec(
            "docker", "compose",
            "-p", f"oj-plugin-{self.name}",
            "-f", str(compose_file),
            "down", "--remove-orphans",
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE,
        )
        await proc.communicate()

    def get_routers(self):
        """兼容内置 + 外部两种部署方式"""
        try:
            # 场景 A：内置插件（app.plugins.ocr_plugin 存在）
            from app.plugins.ocr_plugin.api import router
            from app.plugins.ocr_plugin.batch_api import router as batch_router
        except ImportError:
            # 场景 B：外部插件（从 plugins_installed 动态加载）
            import importlib.util
            import sys
            plugin_backend_dir = Path(__file__).parent

            api_spec = importlib.util.spec_from_file_location(
                "_ext_ocr_api", plugin_backend_dir / "api.py"
            )
            api_mod = importlib.util.module_from_spec(api_spec)
            sys.modules["_ext_ocr_api"] = api_mod
            api_spec.loader.exec_module(api_mod)
            router = api_mod.router

            batch_spec = importlib.util.spec_from_file_location(
                "_ext_ocr_batch_api", plugin_backend_dir / "batch_api.py"
            )
            batch_mod = importlib.util.module_from_spec(batch_spec)
            sys.modules["_ext_ocr_batch_api"] = batch_mod
            batch_spec.loader.exec_module(batch_mod)
            batch_router = batch_mod.router

        return [router, batch_router]
```

**`get_routers` 双分支的核心价值**：同一份 `__init__.py` 代码，无论放在 `app.plugins.ocr_plugin`（内置）还是 `plugins_installed/ocr_plugin/backend/`（外部），都能正确 import 到 `api.py` 和 `batch_api.py`。这避免了「内置一套代码、外部一套代码」的维护噩梦。

### 3.5 插件包结构（`.ojplugin`）

```
ocr_plugin.ojplugin (ZIP)
├── manifest.json                    # 元数据
├── docker-compose.yml               # 微服务编排（image 引用预构建镜像）
├── backend/
│   ├── __init__.py                  # OcrPlugin，兼容内置/外部
│   ├── api.py                       # /parse 接口
│   ├── batch_api.py                 # /batch-import 接口
│   └── requirements.txt             # 空文件（Day 52 无额外 pip 依赖）
├── service/                         # 微服务源码（供离线重建）
│   ├── Dockerfile
│   ├── main.py
│   └── requirements.txt
└── frontend/
    └── index.html                   # 占位
```

**关键变更**：`docker-compose.yml` 内部**不写 `build`**，写 `image`：

```yaml
services:
  ocr-service:
    image: oj-plugin-ocr_plugin-service:0.3.0    # 预构建镜像，不再 build
    container_name: oj-plugin-ocr_plugin-service
    volumes:
      - ./data/paddle_models:/root/.paddleocr
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
    restart: unless-stopped
    networks:
      - oj-network

networks:
  oj-network:
    external: true
    name: oj-platform_default
```

**为什么放弃 `build`**：

`docker compose -f /app/plugins_installed/ocr_plugin/docker-compose.yml up` 在 **backend 容器内**执行时，`build: ./service` 被解析成容器内路径 `/app/plugins_installed/ocr_plugin/service`，然后**作为 build context 传给宿主机 Docker Daemon**。宿主机不认识 `/app/plugins_installed/...`，会报 `bind source path does not exist`。

**解决方案**：
1. `pack_ocr_plugin.py` 在**宿主机**上预先 `docker build -t oj-plugin-ocr_plugin-service:0.3.0` 构建镜像（build context 是宿主机路径，正常）
2. 插件 compose 里只写 `image`，不写 `build`
3. 卸载时镜像保留，下次安装秒起

### 3.6 前端卸载按钮（`frontend/src/views/Settings.vue`）

在「已安装的扩展插件」卡片中为每个插件添加「卸载」按钮：

```vue
<button
  class="btn-ghost uninstall-btn"
  @click="onUninstallPlugin(p)"
  :disabled="uninstalling"
>
  {{ uninstalling ? '卸载中...' : '卸载' }}
</button>
```

```typescript
const uninstalling = ref(false)

async function onUninstallPlugin(p: any) {
  const folderName = p.folder_name || p.name
  if (!confirm(`确定要卸载 ${p.display_name || p.name} 吗？\n\n这会销毁插件的微服务容器（Docker 镜像保留）。`)) {
    return
  }
  uninstalling.value = true
  try {
    const adminKey = localStorage.getItem('admin_key') || ''
    await api.delete(`/admin/market/uninstall/${folderName}`, {
      headers: { 'X-Admin-Key': adminKey }
    })
    alert('插件已卸载，页面将刷新。')
    window.location.reload()   // 让导航栏菜单消失
  } catch (e: any) {
    alert('卸载失败：' + (e.response?.data?.detail || e.message || e))
  } finally {
    uninstalling.value = false
  }
}
```

**为什么卸载后 `window.location.reload()`**：卸载删除了外部插件目录，`/api/plugins/ui` 下次返回不再包含 `ocr_plugin`；但 FastAPI 的 `app.routes` 还在内存中（运行期不能动态卸载路由）。**刷新页面后，导航栏重新从 `/api/plugins/ui` 拉数据，菜单自然消失**。用户不会看到失效的菜单项。

## 四、踩坑全记录（七个关键坑）

### 坑 1：内置 + 外部插件同名冲突

**现象**：把 `OCR_SERVICE_HEALTH` 改成 `/openapi.json` 后，UI 安装依然 500 超时。

**根因**：`ocr_plugin` 同时存在于：

| 路径 | 类型 | 加载方式 |
|---|---|---|
| `backend/app/plugins/ocr_plugin/` | 内置 | `discover("app.plugins")` 用 `pkgutil.iter_modules` 扫描 |
| `backend/plugins_installed/ocr_plugin/` | 外部 | `discover_external` 用 `importlib.util.spec_from_file_location` 加载 |

加载顺序：
1. `main.py` 顶层 `discover("app.plugins")` → 触发 `@register_plugin` → `_plugin_classes` 里加入内置 `OcrPlugin`
2. `_build_instances()` → 实例化 → `_plugins['ocr_plugin']` 是**内置版本**
3. 用户点击安装 → `install_plugin()` → `reload_external()` → `discover_external` 发现 `ocr_plugin` 已存在 `sys.modules` → **跳过**
4. `_build_instances()` 里 `if instance.name not in self._plugins` → `ocr_plugin` 已存在 → **跳过**
5. `on_install` 用的是**内置版本**，其 `OCR_SERVICE_HEALTH` 是 `/health` → 404 → 超时

**数学化的表现**：设 \(P_{in}\) 为内置版本，\(P_{out}\) 为外部版本，\(\text{install\_plugin}(P)\) 实际使用的是：

\[
\text{effective} = \begin{cases} P_{in} & \text{if } P_{in} \in \_plugins \text{ (always true after startup)} \\ P_{out} & \text{otherwise} \end{cases}
\]

这导致无论怎么改外部代码，只要内置目录存在，就永远用的是旧的。

**解决方案**：彻底移走内置目录。

```cmd
mkdir backend\app\_ocr_plugin_removed
move backend\app\plugins\ocr_plugin backend\app\_ocr_plugin_removed\ocr_plugin
```

**为什么用 `_ocr_plugin_removed` 而非直接删除**：
- 前缀 `_` 保证 Python `pkgutil.iter_modules` 不扫描（虽然 `app.plugins` 不在这里，但两层保险）
- 保留源码用于历史参考和快速恢复
- `backend/Dockerfile` 的 `COPY . .` 会一起带进镜像，不占额外处理

**教训**：**一个功能不能同时存在于内置和外部两处**。内置插件和外部插件在 `PluginRegistry._plugins` 里共享同一个字典键，先到先得。这是架构设计时的隐含假设，Day 52 才暴露。

### 坑 2：`get_routers` 硬编码内置 import 路径

**现象**：移动内置目录后，backend 启动直接崩溃。

```
File "/app/plugins_installed/ocr_plugin/backend/__init__.py", line 100, in get_routers
    from app.plugins.ocr_plugin.api import router
ModuleNotFoundError: No module named 'app.plugins.ocr_plugin'
```

**根因**：Day 50 写 `__init__.py` 时，`get_routers` 用的是 `from app.plugins.ocr_plugin.api import router`——这是内置时代假设的绝对导入路径。外部插件加载后，`__name__` 是 `ext_plugin_ocr_plugin`，不在 `app.plugins` 命名空间下，绝对导入失效。

**数学化理解**：Python import 系统的模块解析：

\[
\text{import}(M) \to \text{sys.modules} \to \text{sys.path} \to \text{importlib.find\_spec}
\]

`app.plugins.ocr_plugin` 在 `sys.path` 是 `/app/app/` 时能解析，但外部插件在 `/app/plugins_installed/ocr_plugin/backend/` 下，`sys.path` 没有这个目录，所以解析失败。

**解决方案**：`try/except` 双分支：

```python
def get_routers(self):
    try:
        from app.plugins.ocr_plugin.api import router
        from app.plugins.ocr_plugin.batch_api import router as batch_router
    except ImportError:
        import importlib.util
        import sys
        plugin_backend_dir = Path(__file__).parent
        # 用 Path(__file__).parent 拿绝对路径，绕过 sys.path
        api_spec = importlib.util.spec_from_file_location("_ext_ocr_api", plugin_backend_dir / "api.py")
        api_mod = importlib.util.module_from_spec(api_spec)
        sys.modules["_ext_ocr_api"] = api_mod
        api_spec.loader.exec_module(api_mod)
        router = api_mod.router
        # 同样的方式加载 batch_api.py
        ...
    return [router, batch_router]
```

**为什么动态加载不直接用 `importlib.import_module("_ext_ocr_api")`**：`_ext_ocr_api` 不在任何 `sys.path` 目录里，只能通过 `spec_from_file_location` 从文件路径直接加载，并且要**手动注册到 `sys.modules`**，否则模块内部互相 import 时会失败。

**教训**：插件代码中**永远不要写死 `from app.plugins.xxx` 这样的绝对导入路径**。要么全部用相对导入（`from .api import router`），要么用 `Path(__file__).parent` 动态加载。相对导入在 `importlib.util.spec_from_file_location` 场景下也不会生效（因为没有包上下文），所以**动态加载是唯一通用的方案**。

### 坑 3：`docker compose` 在 backend 容器里不存在

**现象**：`[OcrPlugin] compose up failed` 后跟一大段 `docker --help` 帮助文本（`compose` 被当作无效子命令）。

**根因**：`backend/Dockerfile` 只 COPY 了 `docker` CLI 二进制，没 compose 插件。Day 45 判题系统只用 `docker run`，所以没暴露。

**`docker compose` 命令的底层机制**（这是理解方案的关键）：

Docker CLI（`/usr/local/bin/docker`）本身**不含** compose 功能。当执行 `docker compose xxx` 时：

1. Docker CLI 先在 `/usr/local/libexec/docker/cli-plugins/` 和 `~/.docker/cli-plugins/` 查找名为 `docker-compose` 的可执行文件
2. 找到后，将 `xxx` 及后续参数转发给 `docker-compose` 二进制执行
3. 找不到，则打印「'compose' is not a docker command」

所以**只放 `docker` 二进制是不够的**，必须还有 `docker-compose` 插件二进制在 CLI 插件路径下。

**三层验证**：

| 验证命令 | 含义 |
|---|---|
| `docker --version` | Docker CLI 存在 |
| `docker compose version` | Compose 插件被正确识别 |
| `docker-compose version` | 直接调用 compose 二进制（不经过插件机制） |

只有 `docker compose version` 成功才算彻底打通。

**解决方案**（两条路径）：

**临时**（当前容器）：
```cmd
docker cp docker-compose-linux oj-platform-backend-1:/usr/local/libexec/docker/cli-plugins/docker-compose
docker exec oj-platform-backend-1 chmod +x /usr/local/libexec/docker/cli-plugins/docker-compose
```

**持久化**（Dockerfile）：
```dockerfile
COPY docker-compose-linux /usr/local/libexec/docker/cli-plugins/docker-compose
RUN chmod +x /usr/local/libexec/docker/cli-plugins/docker-compose \
    && rm -f /app/docker-compose-linux
```

**教训**：**任何容器内需要长期存在的文件，必须走 Dockerfile 的 COPY，绝不能依赖 `docker cp` 到运行容器的可写层**。可写层的生命周期与容器相同，容器一旦被重建（`docker compose build` 后 `up`），可写层被新镜像覆盖，`docker cp` 的内容全部丢失。

### 坑 4：健康检查端点不存在

**现象**：微服务日志大量 `GET /health HTTP/1.1 404 Not Found`，`on_install` 30 次轮询全部失败。

**根因**：Day 51 的 `service/main.py` 只定义了 `@app.post("/ocr")`，没有 `/health`。`OcrPlugin.on_install` 的健康检查打到 `/health`，拿 404。

**为什么不能直接重建镜像**：Day 51 的镜像基于 `nvidia/cuda:12.1.0-cudnn8-runtime`，依赖层 `pip install torch==2.4.1+cu121`（798.9MB）需要重新下载，耗时 30-60 分钟。不值得为了加一行 `/health` 路由重建整个镜像。

**解决方案**：改用 FastAPI **默认暴露**的 `/openapi.json`：

```python
OCR_SERVICE_HEALTH = f"{OCR_SERVICE_URL}/openapi.json"
```

`/openapi.json` 是 FastAPI 自动生成的 OpenAPI 3.0 描述文件，**任何 FastAPI 应用都会暴露它**，无需手写路由。它返回 200 JSON，正好用于健康探测。

**数学化理解**：设 \(S\) 为 FastAPI 应用，\(R\) 为其路由集合。FastAPI 启动时：

\[
R = R_{\text{user}} \cup \{\text{/docs}, \text{/redoc}, \text{/openapi.json}\}
\]

`/openapi.json` 永远存在，即使 `R_{\text{user}} = \emptyset`。

**教训**：插件健康探测应优先使用「协议级/框架级」端点（如 `/openapi.json`、`/docs`），而不是业务自定义端点。业务端点可能因为版本差异、代码变更而失效。

### 坑 5：`pack_ocr_plugin.py` 的 `SRC_PLUGIN` 路径

**现象**：移动 `ocr_plugin` 到 `_ocr_plugin_removed` 后，`python scripts/pack_ocr_plugin.py` 报 `FileNotFoundError`。

**根因**：`SRC_PLUGIN` 常量硬编码了 `backend/app/plugins/ocr_plugin` 路径。

**解决方案**：
```python
SRC_PLUGIN = ROOT / "backend" / "app" / "_ocr_plugin_removed" / "ocr_plugin"
```

**教训**：目录重构时，**所有引用该目录的脚本都要同步更新**。这次只涉及 `pack_ocr_plugin.py`，但如果将来有 `test_ocr.py`、`lint_ocr.sh` 之类的脚本，也会一起坏掉。**目录重构的隐含成本是「所有引用者要跟着改」**。

### 坑 6：Docker Hub 拉不动 + 加速器失效

**现象**：
```cmd
docker pull docker/compose:2.29.7
Error response from daemon: unknown: failed to resolve reference "docker.io/docker/compose:2.29.7": 
unexpected status from HEAD request to https://docker.xuanyuan.me/v2/docker/compose/manifests/2.29.7?ns=docker.io: 403 Forbidden
```

**根因**：
1. 直连 Docker Hub 慢/超时
2. `docker.xuanyuan.me` 加速器返回 403（可能因为服务关闭或限流）
3. 国内多个加速器（DaoCloud、1ms.run 等）**对 `docker/compose` 这种官方镜像的 pull 支持不稳定**

**解决方案**：绕过 Docker Hub，直接从 GitHub Release 下载 Linux 二进制：

```cmd
curl -L -o docker-compose-linux "https://ghfast.top/https://github.com/docker/compose/releases/download/v2.29.7/docker-compose-linux-x86_64"
```

`ghfast.top` 是 GitHub 代理，11 秒下载完成 63.7MB。

**关键参数**：`-L` 跟随重定向（GitHub Release 会 302 到对象存储，不跟随会拿到 302 响应头，下载到几百字节的错误页）。

**教训**：**构建镜像不一定要拉镜像**。对于只需要单个二进制的场景（如 `docker-compose`），**直接从 GitHub Release 下载二进制更快、更可靠**。`docker/compose:2.29.7` 镜像里 90% 是 alpine 系统文件，我们只需要 `/usr/local/bin/docker-compose` 一个文件，下载 60MB 的镜像就浪费了。

### 坑 7：`docker compose build` 重建 backend 导致 compose 二进制丢失

**现象**：`docker cp` 注入 compose 成功后，`docker compose build backend worker` 完，又变成 `docker: 'compose' is not a docker command`。

**根因**：
1. `docker cp` 修改的是**容器可写层**（overlayfs 上层）
2. `docker compose build backend` 构建新镜像，`docker compose up -d backend` 用新镜像创建**新容器**
3. 新容器的可写层是空白的，`docker cp` 的成果自然消失

**数学化理解**：设镜像为 \(I\)，容器为 \(C\)，可写层为 \(W\)，则容器文件系统：

\[
FS(C) = I \cup W
\]

`docker cp` 写入 \(W\)。`docker compose build` 产生新镜像 \(I'\)。`docker compose up -d` 创建新容器 \(C'\)，其文件系统：

\[
FS(C') = I' \cup W' = I' \cup \emptyset
\]

**\(W\) 中的修改全部丢失**。

**解决方案**：修改 Dockerfile，把 `docker-compose-linux` 用 `COPY` 打进镜像层 \(I\)：

\[
FS(C) = I_{\text{含 compose}} \cup W
\]

这样即使 `docker compose build` 重建 \(I\)，只要 Dockerfile 里的 `COPY` 指令还在，\(I'\) 依然包含 compose。

**教训**：**这是一条铁律 —— 容器内任何需要长期存在的文件，必须通过 Dockerfile `COPY` 注入镜像层，绝不能依赖 `docker cp` 到运行容器**。可写层只用于临时调试，不能作为持久化手段。
