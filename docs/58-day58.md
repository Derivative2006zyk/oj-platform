# 第 58 天：并发冲突解决与乐观锁（Version 字段）

### 一、今日目标
- 解决多端同时编辑同一道题目时，后保存的一方会覆盖先保存一方数据的“丢失更新（Lost Update）”问题。
- 引入乐观锁机制（Version 字段），在数据库层面拦截并发的写操作。
- 前端配合展示冲突提示，引导用户刷新后重试。

### 二、核心实现

#### 1、数据库模型升级
- 在 `Problem` 模型中增加 `version` 字段，默认值为 1，且不允许为空。
- 新增 Alembic 迁移文件 `e10aeed469af_add_version_to_problems.py`。为了防止老数据出现 null 报错，强制添加了 `server_default='1'`。

#### 2、服务层并发控制
- 修改 `update_problem`：在真正执行 update 之前，校验前端传上来的 `version` 是否等于数据库当前的 `version`。
- 如果版本号不匹配（说明在此期间有其他设备修改了该数据），直接抛出 `HTTPException(status_code=409)`。
- 如果版本号一致，允许更新，并在更新成功后执行 `problem.version += 1`。

#### 3、接口层与前端联动
- `ProblemUpdate` 和 `ProblemDetail` 两个 Schema 都加入了 `version` 字段。
- 前端 `ProblemEdit.vue` 在 `onMounted` 时记录题目的 `version`，提交时一并带上。
- 在前端的 `catch` 块中单独捕获 `409` 状态码，当发生冲突时，拦截默认的保存失败提示，弹窗提醒用户“该题目已被其他设备修改，请刷新后重试”。

### 三、踩坑记录

#### 1、Alembic 历史断层（找不到 revision）
**现象**：执行 `alembic upgrade head` 时报 `Can't locate revision identified by '79fdf72a1cbd'`，后端陷入无限重启。
**原因**：之前某次生成的迁移文件被误删或没提交，导致数据库记录的版本号在代码库中找不到对应的文件。
**解决**：强行更新数据库里的 `alembic_version` 表，把版本号拨回当前现存的最新版本，再继续升级。

#### 2、旧数据导致的非空约束报错
**现象**：迁移时添加 `version` 字段报错 `column "version" contains null values`。
**原因**：数据库里已经有了旧题目，给表加一个不能为空的字段，数据库不知道旧数据的该字段该填什么。
**解决**：在 Alembic 迁移脚本中增加 `server_default='1'`，让数据库自动给旧数据填充初始值。

#### 3、迁移文件在容器内无法直接编辑
**现象**：在容器内生成的迁移文件，宿主机找不到。
**解决**：使用 `docker cp` 从容器将文件拷回宿主机，修改后再次 `docker cp` 覆盖回容器。
