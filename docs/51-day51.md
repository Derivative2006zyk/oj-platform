# 第 51 天：视觉算法优化与 GPU 极速推理

### 一、今日目标

- 彻底重构 OCR 微服务，将其从单纯的文字提取升级为“版面分析 + 公式识别”的双引擎视觉管线。
- 打通 Windows 宿主机与 Docker 容器底层的 WSL2 GPU 直通，利用 RTX 5070 的 CUDA 算力实现大模型的高速推理。
- 解决复杂的底层动态链接库冲突（cuDNN 版本地狱）以及网络镜像源导致的依赖劫持问题。
- 前端引入 MathJax 渲染引擎，并基于占位符保护与语法校验算法，实现极强鲁棒性的 LaTeX 容错渲染。

### 二、GPU 环境与底层基础设施重构

在纯 CPU 环境下运行包含 Transformer 架构的视觉模型（如 pix2tex）时，单张图片的推理延迟高达数分钟，完全无法满足工程可用性。为此，必须打通 Docker 容器与宿主机 GPU 的物理壁垒。

#### 1. WSL2 环境修复与 GPU 直通验证
在进行容器化 GPU 挂载前，必须确保 WSL2 能够正确识别 Windows 侧的 NVIDIA 驱动。若出现 `execvpe(nvidia-smi) failed: No such file or directory` 错误，通常是因为 WSL 的挂载路径未正确注册。
通过创建软链接修复：
```bash
sudo ln -s /usr/lib/wsl/lib/nvidia-smi /usr/bin/nvidia-smi
```
随后在容器内运行官方测试镜像：
```bash
docker run --rm --gpus all nvidia/cuda:11.8.0-base-ubuntu22.04 nvidia-smi
```
成功输出 RTX 5070 的 GPU 拓扑表，证实了 Docker Engine 通过 `libnvidia-container` 成功将宿主机的 `/dev/nvidia*` 设备节点挂载到了容器内部。

#### 2. 基础镜像的选型：CUDA 与 cuDNN 的匹配
由于 RTX 5070 基于最新的 Blackwell 架构，必须使用较新的 CUDA 工具包。我们将微服务的基础镜像从 `python:3.10-slim` 替换为：
```dockerfile
FROM nvidia/cuda:12.1.0-cudnn8-runtime-ubuntu22.04
```
这使得容器内不仅包含了 CUDA 12.1 的运行时库（`libcudart.so` 等），还预置了 cuDNN 8.x，为后续 PyTorch 的安装提供底层支撑。

#### 3. PyTorch 的依赖陷阱与分步安装策略
在安装 `pix2tex` 时，若直接通过国内的阿里云或清华源安装 `torch==2.4.1`，常常会引发哈希校验失败或 SSL 拦截（因为官方源被墙）。
解决方案是**分步安装**：
```dockerfile
# 第1步：从 PyTorch 官方源安装带 CUDA 12.1 的专属 Wheel 包
RUN pip3 install --no-cache-dir \
    torch==2.4.1 \
    torchvision==0.19.1 \
    --index-url https://download.pytorch.org/whl/cu121

# 第2步：从国内源安装其余依赖
RUN pip3 install --no-cache-dir -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/
```

### 三、cuDNN 版本地狱：动态链接库的加载冲突与破局

这是今日最棘手的技术难点。
`pix2tex` 所依赖的 PyTorch 2.4.1（CUDA 12.1）默认强依赖 `cuDNN 9.1`。而 `paddlepaddle-gpu==2.6.2` 官方编译时链接的是 `cuDNN 8.6`。
当两者处于同一容器内时，发生了经典的 ABI（应用二进制接口）冲突。若系统优先加载了 PyTorch 的 cuDNN，Paddle 就会报 `Cannot load cudnn shared library`；反之若强行降级 cuDNN 至 8.9，PyTorch 则会因为找不到 `libcudnn.so.9` 而直接 `Segmentation fault`。

#### 1. 破局思路：架构层面的功能降级与解耦
为了彻底避开动态库打架，我们决定**在架构层面分离计算任务**：
- **PaddleOCR 退居幕后**：仅利用其强大的轻量化文本检测模型（DB-ResNet），在 CPU 上执行版面分析，切出所有文本行的坐标（Bounding Box）。CPU 处理此任务的耗时在 `50ms` 级别，对整体延迟影响极小。
- **pix2tex 全量接管 GPU**：将裁剪出来的纯公式块送入 ViT 模型，利用 RTX 5070 满血推理。

#### 2. `LD_LIBRARY_PATH` 的暴力注入
虽然 Paddle 退居 CPU，但如果在同一进程中 `import torch` 和 `import paddle`，底层的 C++ 库依然会冲突。我们通过在 `Dockerfile` 中强制指定 PyTorch 专属的库路径来破局：
```dockerfile
ENV LD_LIBRARY_PATH=/usr/local/cuda/lib64:/usr/lib/x86_64-linux-gnu:/usr/local/lib/python3.10/dist-packages/nvidia/cudnn/lib:/usr/local/lib/python3.10/dist-packages/nvidia/cublas/lib:$LD_LIBRARY_PATH
```
此配置确保了当 Python 解析器加载 `libpaddle.so` 时，不会误用 NVIDIA pip 包中的 `.so` 文件，从而实现了两套框架在同一容器内的和平共存。

### 四、视觉算法管线：前置过滤与 LaTeX 幻觉抑制

“幻觉”（Hallucination）不仅存在于大语言模型，视觉 Transformer 同样存在。当输入图片既包含中文说明、又包含数学公式时，`pix2tex` 的 Decoder 层会强行将其解析为极其复杂的垃圾 LaTeX（如 `\frac{\partial \phi}{\partial \phi}` 反复循环）。

#### 1. 数学特征提取与前置过滤
我们在微服务中引入了一个轻量级的启发式判断函数 `should_use_latex_model`。
设输入文本为 \(S\)，计算其包含的中文字符数 \(C_{zh}\)。
若 \(C_{zh} > 3\)，或者 \(S\) 为纯英文且无特殊符号，则直接拦截，保留 PaddleOCR 的原生识别结果。
只有当 \(S\) 包含诸如 \(\in, \sum, \int, =, <, >\) 等明显数学符号时，才允许进入 ViT 模型：
$$
f(S) = \begin{cases} 
\text{pass}, & \text{if } C_{zh} \le 3 \land |S_{math\_symbols}| > 0 \\
\text{block}, & \text{otherwise}
\end{cases}
$$

#### 2. 输出时的 LaTeX 拓扑修复
ViT 模型由于自回归生成的特性，偶尔会遗漏闭合的括号。我们在输出层添加了 `fix_latex_braces` 算法：
遍历生成的 LaTeX 字符串 \(L\)，统计左大括号 \(N_{left}\) 与右大括号 \(N_{right}\)。
若 \(N_{left} \neq N_{right}\)，则直接判定该公式解析失败，将其降级为纯文本，防止前端渲染器崩溃。

### 五、前端渲染：占位符替换与 MathJax 极强容错

传统 Markdown 解析器（如 `marked`）在处理公式时，常常会将由 `$$` 包裹的公式块错误地解析为 `<p>$$ ... $$</p>`，或者在遇到含有 `_`（下划线）的公式时，错误地将其转换为斜体 `<em>`，导致公式彻底损坏。

#### 1. 状态机式的占位符保护
我们在 `MarkdownRenderer.vue` 的计算属性中，采用了类似于编译器词法分析的预处理策略：
1. 利用正则 `/\$\$([\s\S]*?)\$\$/g` 提取所有块级公式。
2. 将它们替换为唯一的标识符（如 `@@BLOCK_MATH_0@@`），存入临时数组。
3. 将剩余的 Markdown 文本交给 `marked` 进行 HTML 转化。
4. 在最终的 HTML 字符串中，将标识符还原为原始的 `$$ ... $$`。

公式的提取集合映射关系可表示为：
$$
\forall M_i \in \{BlockMath\}, \quad M_i \xrightarrow{encode} T_i \xrightarrow{marked} HTML \xrightarrow{decode} M_i
$$

#### 2. MathJax 的错误边界处理
即便公式被安全保护，若公式本身存在语法错误（如未闭合的 `\left\{`），MathJax 默认会抛出一个 `Extra close brace or missing open brace` 的严重 DOM 错误，并中断后续所有公式的渲染。
我们在 `index.html` 中激活了 `noerrors` 宏包，并配置了 `skipHtmlTags`：
```javascript
window.MathJax = {
  tex: {
    packages: {'[+]': ['noerrors']},
    inlineMath: [['$', '$'], ['\\(', '\\)']],
    displayMath: [['$$', '$$'], ['\\[', '\\]']]
  },
  options: {
    skipHtmlTags: ['script', 'noscript', 'style', 'textarea', 'pre', 'code']
  }
};
```
配合前端 `sanitizeMath` 函数预先剔除括号不匹配的公式，确保了即使面对最恶劣的 OCR 识别结果，前端页面也能像打不死的“小强”一样稳定渲染，不再出现大面积的黄色红字崩溃。

### 六、踩坑记录与工程沉淀

1. **WSL 系统损坏导致 Docker 掉线**
   **现象**：执行 `wsl -e free -h` 时报 `ERROR_FILE_NOT_FOUND`，Docker 管道断开。
   **解决**：通过微软商店重新安装 Ubuntu 分发版，并在 Docker Desktop 中重新勾选 WSL 集成。
2. **模型权重下载被墙**
   **现象**：容器启动时报 `Connection refused`，无法从 GitHub 拉取 `weights.pth`。
   **解决**：手动在宿主机浏览器下载权重，利用 Dockerfile 的 `COPY` 指令在构建阶段将其静态挂载进镜像。
3. **NVIDIA 显卡驱动版本过低**
   **现象**：镜像拉取后启动容器报错 `could not select device driver ""`。
   **解决**：更新 Windows 侧最新的 NVIDIA 驱动，并在 WSL 中验证 GPU 设备节点。
