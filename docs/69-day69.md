# 第 69 天：离线优先全链路加固

### 一、今日目标

第 68 天解决了“连不上时界面难看”的问题，但离线优先只覆盖了列表读取缓存。写操作（录入、编辑、删除）在断网时是直接报错还是进入本地队列，从未完整验证；图片上传、判题提交、题库导入在断网时的行为也不明确。

今日三个目标：

1. **审计写路径**：逐一确认断网行为，明确哪些进入本地队列、哪些直接拒绝
2. **补齐队列能力**：重试计数、冲突标记、死信区，避免“失败就丢”或“无限重试”
3. **补上可观测性**：全局离线条 + 待同步数量，让用户知道数据处于什么状态

### 二、核心实现

#### 1、写操作分流的判定原则

**可重放的幂等写进队列，破坏性或依赖服务端的操作直接拒绝。**

```ts
export function shouldQueue(method: string, url: string): boolean {
  const m = method.toUpperCase()

  if (m === 'DELETE') return false
  if (url.includes('/submissions')) return false
  if (url.includes('/admin/images')) return false
  if (url.includes('/admin/bank/import')) return false
  if (url.includes('/plugins/llm_ocr/parse')) return false
  if (url.includes('/plugins/ai/chat')) return false

  return url.includes('/admin/problems')
}
```

各路径的处理结论：

| 路径 | 断网行为 | 理由 |
|---|---|---|
| 录入题目 | 入队 | 纯写入，恢复后可重放 |
| 编辑题目 | 入队 | 带 version，冲突可检出 |
| 删除题目 | 直接拒绝 | 破坏性操作，无法撤销 |
| 图片上传 | 直接拒绝 | 依赖服务端存储，本地无意义 |
| 提交判题 | 入队（走 `submission.ts` 自己的分支） | 判题结果需服务端，但答案不丢 |
| 题库导入 | 直接拒绝 | 文件依赖服务端解析 |
| OCR 识别 | 直接拒绝 | 需调用外部视觉模型 |

#### 2、队列结构升级

原有结构只有 `id / method / url / data / description`，失败后无法区分“网络问题”与“参数错误”，也无法统计重试次数。

```ts
export interface OfflineAction {
  id: string
  method: 'post' | 'put' | 'delete'
  url: string
  data?: any
  headers?: Record<string, string>
  description: string
  createdAt: number      // 新增：用于展示与排序
  attempts: number       // 新增：重试计数
  lastError?: string     // 新增：失败原因
  status: QueuedStatus   // 新增：pending | conflict | dead
}
```

`enqueueAction` 的入参改为 `Omit<..., 'id' | 'createdAt' | 'attempts' | 'status'>`，内部统一生成，避免调用方各写一套 id 规则。

#### 3、回放策略：按错误类型分流

这是今日改动最核心的部分。

```ts
for (const action of queue) {
  try {
    const { default: api } = await import('./axios')
    await api.request({ ... })
    removeActionFromQueue(action.id)
    synced += 1
  } catch (e: any) {
    const status = e?.response?.status

    // 仍然断网：计数后保留，下轮再试
    if (!e.response || e.code === 'ERR_NETWORK' || e.message?.includes('timeout')) {
      updateAction(action.id, { attempts: action.attempts + 1, lastError: '网络不可用' })
      continue
    }

    // 冲突：不自动覆盖，标记等待人工处理
    if (status === 409) {
      updateAction(action.id, {
        status: 'conflict',
        lastError: '内容已被其他设备修改',
      })
      continue
    }

    // 其他 4xx：参数错误，重试无意义
    if (status && status >= 400 && status < 500) {
      updateAction(action.id, {
        status: 'dead',
        lastError: e?.response?.data?.detail || `请求失败（${status}）`,
      })
      continue
    }

    // 5xx：计数，超过上限进死信
    const attempts = action.attempts + 1
    updateAction(action.id, {
      attempts,
      status: attempts >= MAX_ATTEMPTS ? 'dead' : 'pending',
      lastError: e?.message || '服务端错误',
    })
  }
}
```

关键设计点：

- **409 不自动合并**：冲突意味着服务端已有更新版本，静默覆盖会丢数据
- **4xx 直接死信**：参数错误重试一百次也不会成功
- **5xx 有上限**：`MAX_ATTEMPTS = 5`，避免服务端故障时无限重试拖垮前端

#### 4、axios 拦截器接入入队

```ts
if (config && isNetworkError(error) && shouldQueue(method, url)) {
  const headers: Record<string, string> = {}
  const adminKey = localStorage.getItem('admin_key')
  if (adminKey) headers['X-Admin-Key'] = adminKey

  let data = config.data
  if (typeof data === 'string') {
    try { data = JSON.parse(data) } catch {}
  }

  const action = enqueueAction({ method, url, data, headers, description })
  return Promise.resolve(makeQueuedResponse(config))
}
```

返回 202 语义的伪响应 `{ __queued__: true }`，让调用方能区分“已入队”与“真正成功”：

```ts
export function isQueued<T>(data: T | QueuedResult): data is QueuedResult {
  return !!data && typeof data === 'object' && (data as any).__queued__ === true
}
```

#### 5、全局离线条

`App.vue` 中依据三个来源决定是否显示：

```ts
const showBar = computed(
```

文案按优先级切换：待同步 → 冲突 → 失败。切换动作通过 `offline-queue-changed` 事件驱动：

```ts
function saveQueue(queue: OfflineAction[]) {
  localStorage.setItem('oj_cache_' + QUEUE_KEY, JSON.stringify({ savedAt: Date.now(), data: queue }))
  window.dispatchEvent(new Event('offline-queue-changed'))
}
```

### 三、踩坑记录

#### 1、循环依赖导致运行时崩溃

**现象**：`npm run build` 能过，但运行时 Console 报 `Cannot access 'api' before initialization`。
**原因**：`offline-queue.ts` 顶层 `import api from './axios'`，而 `axios.ts` 又 `import { enqueueAction } from './offline-queue'`。ESM 循环引用下，模块初始化顺序决定谁拿到 `undefined`。
**解决**：队列侧去掉顶层 import，在 `processQueue` 内动态引入：

```ts
const { default: api } = await import('./axios')
```

回放本身是延迟执行，动态引入既解耦又不影响性能。

#### 2、接口签名变更导致的连带报错

**现象**：`submission.ts:40` 报 `'id' does not exist in type 'Omit<OfflineAction, ...>'`。
**原因**：`enqueueAction` 改为内部生成 `id`，但 `submission.ts` 的离线提交分支仍手动传 `id`。
**解决**：删除调用处的 `id` 字段；用 `findstr` 全量扫描 `enqueueAction` 调用点，确保无遗漏。

#### 3、无泛型的辅助函数导致 TS6133

**现象**：`axios.ts:40` 报 `'T' is declared but its value is never read`。
**原因**：`makeQueuedResponse<T>(config)` 声明了泛型但函数体未使用。
**解决**：去掉泛型。

#### 4、两套 compose 端口冲突

**现象**：`docker compose up -d` 报 `Bind for 0.0.0.0:6379 failed: port is already allocated`，随后 Vite 代理报 `ECONNREFUSED 127.0.0.1:8000`。
**原因**：桌面端那套 `oj-platform-desktop-*` 仍在运行，占了 6379/5432/8000。这是第 68 天隔离方案的预期副作用——容器和数据隔离了，但端口仍共用。
**解决**：切换环境前必须先停另一套：

```bat
:: 切到开发环境
taskkill /IM oj-platform-desktop.exe /F
docker compose -f "%APPDATA%\oj-platform\docker-compose.desktop.yml" -p oj-platform-desktop down
docker compose up -d

:: 切到桌面端
docker compose down
```

#### 5、旧的离线判断条件失效

**现象**：`ProblemEdit.vue` 里用 `res.message === 'offline-saved'` 判断离线保存，但永远不会命中。
**原因**：axios 拦截器返回的是 `{ __queued__: true, queued: true }`，与旧的 `offline-saved` 字段名不一致。
**解决**：统一改用 `isQueued(res)`，字段名收敛到一处。
