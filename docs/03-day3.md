# 第3天：Alembic 迁移与预置分类

### 一、迁移工具的必要性

#### 1、问题背景
数据库结构随业务演化而变。若直接修改模型并用 SQL 手动建表，无法追溯历史，也无法在团队间同步。Alembic 提供版本化迁移，每次结构变更生成一个脚本，可升级可回退。

#### 2、核心概念

| 概念 | 说明 |
|---|---|
| revision | 一次迁移，对应一个 Python 脚本 |
| head | 最新版本 |
| base | 初始版本 |
| upgrade | 升级到某版本 |
| downgrade | 回退到某版本 |
| autogenerate | 对比模型与数据库，自动生成脚本 |

类比：Alembic 之于数据库，相当于 Git 之于代码。

### 二、初始化与配置

#### 1、初始化命令
```
cd backend
alembic init alembic
```

生成目录结构：
```
backend/
├── alembic/
│   ├── env.py
│   ├── script.py.mako
│   ├── README
│   └── versions/
└── alembic.ini
```

#### 2、env.py 的关键修改
```python
# backend/alembic/env.py（关键片段）
import asyncio
from logging.config import fileConfig
from sqlalchemy import pool
from sqlalchemy.engine import Connection
from sqlalchemy.ext.asyncio import async_engine_from_config
from alembic import context

from app.database import Base
from app.models import Category, Problem, TestCase, ResearchSubproject, Image
from app.core.config import settings

config = context.config
config.set_main_option("sqlalchemy.url", settings.DATABASE_URL)

if config.config_file_name is not None:
    fileConfig(config.config_file_name)

target_metadata = Base.metadata
```

#### 3、原理分析

| 步骤 | 作用 |
|---|---|
| 导入 Base 与所有模型 | 使 `Base.metadata` 包含全部表定义 |
| set_main_option | 用项目配置覆盖 alembic.ini 中的 URL |
| `target_metadata = Base.metadata` | autogenerate 对比的基准 |

#### 4、异步驱动的处理
因 asyncpg 是异步驱动，alembic 的默认同步调用会报错。解决方式是在 env.py 中区分 offline 与 online 模式，online 模式通过 `asyncio.run` 调用异步引擎：

```python
def do_run_migrations(connection: Connection) -> None:
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        context.run_migrations()

async def run_async_migrations() -> None:
    connectable = async_engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)
    await connectable.dispose()

def run_migrations_online() -> None:
    asyncio.run(run_async_migrations())
```

### 三、迁移的两类用法

#### 1、自动生成
```
alembic revision --autogenerate -m "create all tables"
alembic upgrade head
```

autogenerate 会对比 `Base.metadata` 与数据库当前状态，生成差异脚本。适用于模型驱动建表。

#### 2、手动编写种子数据
```
alembic revision -m "seed default categories"
```

生成的空脚本中填入 SQL：
```python
def upgrade() -> None:
    op.execute("""
        INSERT INTO categories (name, sort_order) VALUES
        ('算法', 1), ('数学', 2), ('物理', 3), ('英语', 4), ('其他', 99)
    """)

def downgrade() -> None:
    op.execute("DELETE FROM categories WHERE name IN ('算法', '数学', '物理', '英语', '其他')")
```

然后 `alembic upgrade head` 应用。

#### 3、场景对照

| 场景 | 用法 |
|---|---|
| 初次建表 | autogenerate |
| 字段变更 | 修改模型后 autogenerate |
| 种子数据 | 手动编写 |
| 数据修正 | 手动编写 |
| 回退 | `alembic downgrade -1` |

### 四、常用命令

| 命令 | 作用 |
|---|---|
| `alembic init alembic` | 初始化 |
| `alembic revision --autogenerate -m "msg"` | 自动生成迁移 |
| `alembic revision -m "msg"` | 生成空迁移 |
| `alembic upgrade head` | 升级到最新 |
| `alembic downgrade -1` | 回退一步 |
| `alembic current` | 显示当前版本 |
| `alembic history` | 显示迁移历史 |

### 六、重置数据库的标准流程

当模型或迁移出现问题时，最干净的做法是清空数据库并重新迁移。

```
cd E:\github_project\oj-platform
docker compose down -v
docker compose up -d
```

删除 `alembic/versions/` 下的所有 `.py` 文件，然后：
```
cd backend
alembic revision --autogenerate -m "create all tables"
alembic upgrade head
alembic revision -m "seed default categories"
# 编辑新生成的种子文件
alembic upgrade head
```

### 七、注意事项

#### 1、迁移命令必须在 backend 目录下执行
- `alembic` 命令默认查找当前目录下的 `alembic.ini`。
- 若在项目根目录执行，会报 "No config file 'alembic.ini' found"。

#### 2、数据库必须先启动
- 执行任何 alembic 命令前，确保容器在运行。
- 检查命令：`docker ps` 显示 `oj-platform-postgres-1` 状态为 `Up`。
- 若报 `ConnectionRefusedError`，先 `docker compose up -d`。

#### 3、env.py 必须导入所有模型
- 若 `app.models` 中遗漏某个模型，autogenerate 不会为该模型生成建表语句。
- 每次新增模型时，记得在 `models/__init__.py` 中导入。

#### 4、autogenerate 的局限
- 不能检测列的重命名，只能识别为"删除旧列+新增新列"。
- 不能检测默认值变化、约束变化等细节。
- 重要迁移必须人工审核生成的脚本。

#### 5、手动迁移的 down_revision
- 生成的空迁移文件中 `down_revision` 指向上一版本。
- 若顺序错乱（如手工编辑），会导致升级链断裂。
- 建议用 `alembic history` 检查迁移链。

#### 6、重置数据库的代价
- `docker compose down -v` 会删除所有数据，**不可恢复**。
- 生产环境严禁使用此命令，只能用于开发环境。

#### 7、单复数陷阱
- 表名统一用复数：`categories`、`problems`、`test_cases`、`research_subprojects`、`images`。
- 若模型中表名不一致，数据库会创建多个表。

#### 8、时间戳的格式
- `server_default=func.now()` 生成的是数据库当前时间。
- 若容器时区与主机不一致，时间戳会偏移。
- 如需指定时区，可用 `server_default=sa.text("now() AT TIME ZONE 'UTC'")`。
