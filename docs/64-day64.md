### 一、今日目标

在前一天，我们打通了基于 SSE 的 AI 流式通用对话接口。但当时的 AI 助教还是一个“孤岛”，用户必须手动复制粘贴题目才能让 AI 解答。今日的核心任务是：**将 AI 能力深度嵌入业务场景，实现上下文自动注入与无感联动。**

具体目标：

2. **智能判题**：针对主观题（证明题），在用户提交证明过程后，一键将“题目 + 用户答案”打包发给 AI 进行批改和挑错。
3. **组件通信重构**：让子组件 `AIChatPanel` 支持父组件通过 `ref` 主动触发消息发送。

### 二、核心实现

#### 1、组件通信：利用 `defineExpose` 暴露触发方法
在 Vue 3 中，子组件默认是封闭的。为了让父组件（题目详情页）能够主动“命令” AI 面板发起提问，我们在 `AIChatPanel.vue` 中暴露了 `triggerQuery` 方法：

```typescript
// AIChatPanel.vue
async function doSend(text: string) {
  if (!text.trim() || loading.value) return
  messages.value.push({ role: 'user', content: text })
  // ... 调用 streamChat 流式接收逻辑 ...
}

// 暴露给父组件的方法
defineExpose({
  triggerQuery(text: string) {
    doSend(text)
  }
})
```

#### 2、业务场景一：一键解析题目
在 `ProblemDetail.vue` 中，我们通过 `ref` 获取 AI 面板实例，并利用 `nextTick` 确保 DOM 渲染完毕后再调用方法：

```typescript
const aiPanelRef = ref<any>(null)

function onExplainProblem() {
  if (!problem.value) return
  showAI.value = true 
  
  // 拼装 Prompt
  const prompt = `请帮我解析这道题，给出详细的解题思路和关键步骤：\n\n【题目】${problem.value.title}\n【描述】\n${problem.value.description}`
  
  // 等待面板渲染完成后触发
  nextTick(() => {
    aiPanelRef.value?.triggerQuery(prompt)
  })
}
```

#### 3、业务场景二：证明题的 AI 智能批改
证明题在 0.2 版本的判题系统中属于“不自动判题”的类型（状态为 SUBMITTED）。现在，我们接入了大语言模型作为“判卷老师”。

我们在证明题作答面板中新增了「让 AI 批改我的证明」按钮，点击后会将用户输入的 `proofText` 和题目信息打包：

```typescript
function onAiJudgeProof() {
  if (!problem.value || !proofText.value.trim()) return
  showAI.value = true
  
  const prompt = `我正在做一道证明题。\n【题目】${problem.value.title}\n【描述】\n${problem.value.description}\n\n【我的证明过程】\n${proofText.value}\n\n请你作为专业的数学老师，帮我批改这段证明，指出逻辑漏洞、不严谨的地方，并给出修改建议。`
  
  nextTick(() => {
    aiPanelRef.value?.triggerQuery(prompt)
  })
}
```

### 三、踩坑记录

#### 1、`nextTick` 与条件渲染的时序问题
**现象**：如果在点击按钮的函数里直接调用 `aiPanelRef.value.triggerQuery()`，会报错 `Cannot read properties of null (reading 'triggerQuery')`。
**原因**：AI 面板使用了 `v-if="showAI"` 控制显隐。当我们把 `showAI` 置为 `true` 时，Vue 的 DOM 更新是异步的。此时面板尚未挂载，`aiPanelRef` 自然为 `null`。
**解决**：必须使用 `nextTick(() => { ... })` 将发送逻辑包裹，等待 Vue 完成 DOM 的 Patch 和挂载后，再执行触发。

#### 2、长上下文与 Token 消耗
**隐患**：我们将整道题的描述（包含大量的 LaTeX 公式代码和样例说明）直接塞给了大模型。如果题目带有超长图片说明或大量样例，可能会瞬间消耗几千个 Token。
**缓解**：目前依赖大模型自身的 32k/128k 上下文窗口能力。如果未来遇到超长题目，可以在前端做截断，或者提示用户手动精简。
